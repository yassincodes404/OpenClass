# Governance

OpenClass is founder-led, community-contributed, and maintainer-reviewed.
The initial Founder / Project Lead is [@yassincodes404](https://github.com/yassincodes404).

| Role                   | Responsibility                                                                 |
| ---------------------- | ------------------------------------------------------------------------------ |
| Founder / Project Lead | Roadmap, official releases, brand, appointments, governance, core architecture |
| Core Maintainer        | Cross-cutting architecture, public protocol, release readiness                 |
| Maintainer             | Review and maintain assigned components                                        |
| Reviewer               | Provide technical feedback within an area of expertise                         |
| Contributor            | Propose and implement improvements                                             |
| Community Member       | Participate in discussion and report issues                                    |

The founder initially performs unassigned maintainer roles. CODEOWNERS records
review responsibility, not exclusive ownership of contributions. Appointments
and removals are announced through repository discussions or issues.

Routine fixes use pull requests. Major decisions use numbered OpenClass RFCs,
including alternatives, evidence, compatibility, safety and migration plans.
Suggested initial RFCs: OC-RFC-0001 Provider Protocol, OC-RFC-0002 Ontology Event Model,
OC-RFC-0003 Automatic Promotion Policy (future work, not permission to activate it).

Maintainers seek documented consensus; the founder resolves deadlock and may
accept or reject proposals with a recorded rationale. Conflicts of interest must
be disclosed; a reviewer should not be the sole reviewer of their own change.
Security matters follow SECURITY.md. Conduct matters follow CODE_OF_CONDUCT.md.

Releases require passing milestone gates and maintainer review; a version label
alone does not establish readiness. Governance changes require an RFC and explicit
founder approval. Source-license rights, including rights to fork, are not
restricted by project governance or brand policy.
